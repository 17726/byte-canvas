# PR154 加载优化的实测取舍

## 调整目标

保留 Arco 组件按需注册。页头、工具栏、属性面板与右键菜单恢复同步导入，使首屏界面的可用时机一致。

这不是判定异步分块一律无效：已有对照显示其额外冷加载收益与暖缓存回退并存，目前优先保留收益更稳定的部分。后续可单独验证低频面板按首次使用加载。

## 已有实验

2026-09-24，三个版本、两个画布场景、两个环境、冷暖缓存，每条件5次，共120次有效加载。2026-11-08重新执行原数据校验通过；本调整没有重跑120次矩阵。

- 基线：`fc3945ecc26aa0e5c734a9250d86357a29b33d89`。
- 完整PR：`f859e8e31ba1c7a69c1f88539ac4de3b730e6f27`。
- 仅Arco：基线仅替换PR的`src/main.ts`并加入`src/plugins/arco.ts`。
- 独立无界面Edge、1440×900、DPR1；相同锁文件与依赖安装，生产构建产物。
- 已有画布固定80个矩形与20个文本；不包含图片、分组、视频或复杂富文本。
- 受限环境同时使用下载1.6Mbps、上传0.75Mbps、延迟150ms、CPU4倍减速，不能把收益单独归因到网络或CPU。
- 冷缓存为新隔离上下文；暖缓存为同上下文第二次导航，恢复相同节点。并非操作系统或进程冷启动。
- 每条件5次，轮换版本顺序，串行执行；缓存命中、节点数量、右键与文本创建真实交互、页面异常与资源稳定性均通过校验。

## 结论

- Arco按需注册贡献了大部分冷加载收益。例如受限100节点场景，基线4972ms，按需注册3033ms，耗时减少约39%。
- 完整PR相对仅Arco，受限冷加载还快约12%～13%；额外收益确实存在，并非“完全无效”。
- 但受限暖缓存中完整PR比仅Arco慢约18%～19%，两个场景每次配对的方向均一致。拆分不能仅凭入口包更小判断总收益。
- 右键与文本创建交互没有显示出一致的明显改善，加载优化不能直接当作编辑交互优化。
- LCP候选主要是Zoom/X/Y状态文字，CLS均为0，不能只用它们判断编辑器界面可用性。
- 每条件只有5次且本机后台负载未隔离，属于描述性实验；不宣称统计显著性或线上指标改善。

## 其他调整

- 移除模块入口的额外`defer`：`type="module"`脚本默认延迟执行，额外属性不提供这里期待的加载收益。
- 移除`* { font-display: swap; }`：`font-display`是`@font-face`描述符，该普通选择器声明不产生预期效果。当前未增加自定义字体加载策略。
- 移除`ignoreDeprecations: "6.0"`：项目TypeScript为5.9，该值导致TS5103；保留现有`baseUrl`与`paths`，不改编译器版本。这属于构建兼容修复，与性能收益分开。
- 保留完整Arco CSS。本次仅调整JS组件注册，未承诺CSS也按需。

参考：[模块脚本执行规则](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script)、[font-display描述符](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/font-display)。
